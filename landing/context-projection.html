How much should the first read return?

How Wuu moved from limiting tool output to reading more only when needed.

Wuu lets a model read a smaller result first and continue reading the source only when it needs to. The starting point is a hard constraint: content that has already entered the conversation history should stay stable. We should not rewrite it carelessly.

Cache hits are the principle

Every step the model takes reads all previous turns again, which is not cheap. To save that cost, inference caches the prefix it has already processed. Later requests can skip recomputation as long as the prefix is unchanged. That creates a hard cost: if any text already in context differs from one turn to the next, the cached prefix before it becomes invalid.

So Wuu’s basic attitude toward history is stability. When a tool finishes, Wuu writes the processed result into history and leaves that content unchanged. Later requests reuse it and only append new material. The cache-hit portion therefore continues across successive turns.

This also creates a problem. Tool calls arrive one after another, and every turn writes new results into history—once written, they are hard to change. Removing or editing them would break the prefix that was already cached. So the value of a tool result declines as context grows: right after it returns, it helps the model confirm the next step; a few turns later, once the task has moved on, it becomes old output sitting in the prefix.

A tool call already has a purpose

Which tool a model calls, and which lines it reads, is usually not random. It comes with a specific question. If it suspects a configuration setting is being ignored, it opens the configuration file. Whether it can move on often depends only on confirming that setting’s value.

So we started paying attention to what the call itself is asking. If the result happens to confirm or correct the judgment the model is holding, the call has done its job. The parts it does not use can wait until it actually needs them.

But there is no ready answer for how much to return. Return too little, and the model cannot get the information it needs to move forward, so it has to read again. Return too much, and we are back where we started: content that enters history becomes a burden a few turns later. We decided to try a smaller default budget first.

Try a smaller budget first

We reviewed collected conversation histories, compared tool outputs of different lengths, and settled on a default projection budget of about 2k tokens.

Smaller results have a direct benefit: each request sends fewer input tokens. Over many turns, the history that later requests carry also shrinks. A larger share of the prefix can hit the cache, so the model does not have to process the same old content every turn.

That is only the input side. The less irrelevant output sits in context, the easier it is for the model to keep sight of the clue that actually determines the next step. Anthropic’s discussion of context rot also notes that accurate recall declines as context grows. A single read may stay below the window limit, but several large outputs can still bury the question the model is trying to answer.

Tool output travels with history into every later request. One result may look small, but the model can find the cause in a log and move on to editing and running checks while that log is still present. Over several turns, old output competes with new evidence—the very burden described above. The smaller the first return, the lighter the load that enters history from the start.

Shrink the returned content, but leave a path to read on

We quickly realized we should not impose too strong a prior on how much a model should read. The Bitter Lesson warns against designs that pre-set an agent’s behavior: you cannot decide in advance that understanding a function requires its callers, or that investigating a log requires the lines around an error. Only the model facing the concrete task can judge that. Hard-coding a “best read size for this moment” mostly makes the decision for it. So we prefer to guess less and leave generous paths to more information, letting the model follow them when it needs to.

A smaller hard limit would also cut off necessary context. The model needs a way to continue reading and fill in the related material.

That is why we built projection. When content must be omitted, Wuu first saves the result of this tool call, or reuses the complete log the command has already left behind. The first view shows only a smaller part, while telling the model how to continue. File content keeps whole lines. Command results retain exit status and key error evidence. When the first view is not enough, the model follows the continuation entry or the saved source.

Return to the configuration example. If the value it reads already explains the problem, the agent can move on. If it sees that the setting references another file, it goes and reads that file. If the omitted part turns out to be the key, it reads that range back.

Save the original result separately for later retrieval

At this point we needed to settle how the whole result is handled. A tool call leaves behind the information it obtained at that moment. To make its next decision, the model only needs to see enough of that result to move the task forward. The two have different uses: the saved result supports later checking and re-reading, while the content entering context supports the decision in front of the model.

If we trimmed the saved copy too, later reading would lose its source. The model might only realize several turns later that a log is useful, or need to re-check a value it did not notice at first. The choices made at first display cannot cover those needs in advance, so we leave the omitted content in the session’s result file. When a command has already saved a complete log, we reuse that log.

What is saved here is the content the tool actually returned for this call. One file read may have requested only a few dozen lines, and the tool itself may have its own read-range and execution limits. Saving this result lets us recover what projection omitted. To learn about other parts of the file, the model still needs to make further reads with explicit ranges.

With that foundation, returned content can be handled case by case. Results whose structure we understand can get a smaller first view organized by lines, entries, and turns. Other results keep the tool’s original form, and only very large text is saved with a preview. Images and attachments take their own path. Together these decisions determine what the model receives each turn.

For file, directory, command, and session results, project by structure

We started with read_file, list_files, bash, and session results. They recur throughout coding work, and their output accumulates easily during repeated exploration. Making their first return compact steadily reduces the old output carried into later requests.

Reading a lot is only one reason. More important, these results have boundaries we understand, and we can always offer an entry point for the next read: files continue by line, directories page by entry, commands leave a log, and sessions can page back to earlier turns. Each time the model receives a part, it knows where to find the rest.

The current file projection keeps the first and last complete lines of the read result and marks the omitted middle. It does not try to guess which line best answers the model’s question. When the model needs the middle, it reads that range. Directory results keep whole entries, so a path is never split from its entry.

Command results have different priorities. Exit status, timeouts, and check results directly affect what the model does next, so they must remain. When shortening output, Wuu reduces ordinary output before error output, and keeps later log lines preferentially. When check information itself is long, the final result may still exceed the preset budget; keeping that information helps the model judge whether the work is complete.

The purpose of reading a session is to hand the thread of a piece of work back to the model. Wuu first takes the recent session summary or the original user request as background, then organizes recent turns around it, and offers an entry to page back. Even a short session read goes through this organization, because only with the full context can the model tell where it had got to and what to do next.

These rules hold because the structure is clear: we know what to keep, which part was omitted, and where the unseen content lives. Other tools’ results are often just one long block of text, with no obvious part that matters more; length alone does not let us make the same trade-offs for them.

Other results keep the tool’s original output

A tool result often reports more than content—it reports progress. An editing result may contain a change that did not actually apply. A collaboration tool tells you who the work went to and what happens next. The body of a loaded skill may be exactly the instructions to follow next. In these results, where the essential information sits has no fixed pattern. Applying the file projection’s “keep the ends” approach could easily cut the sentences the task depends on.

External tools differ even more. Results returned through MCP—whether search hits, a report, or an operation receipt—are structured by the provider. In the same report, the conclusion may sit at the top while the limitations hide at the end or in the body. For unfamiliar structures, Wuu cannot judge which part matters, so it cannot design finer trimming rules.

So for these results, Wuu makes no choice at first. When the text does not exceed the general length or line limits, it is passed through unchanged. Only when it does exceed them does Wuu save the original text, return a short preview, and attach a read entry. This keeps the context footprint down while letting the model retrieve whatever it lacks—rather than guessing for every tool which part matters, we let the model read on demand.

This also affects whether an action can continue smoothly. If the model wants to re-read a report, calling the generating tool again may produce different content. If it wants to check an operation’s receipt, re-running the operation may cause the effect again. After saving the result, re-reading stays on the call that has already completed. The model finds the missing detail, then decides whether the next step needs a new action.

Continuation points to content not yet shown

Saying only “output truncated” still leaves recovery to the model. It has to guess where to read next, and may request the same oversized range again. The continuation entry needs to point at the part not yet shown, so the next call brings new information.

File projection provides read parameters for the omitted middle range. Directory and session results provide the next page. Command output and generic previews can point to the remaining range in the saved result. The model can follow these positions, or narrow the range on its own from clues it has found.

Between two reads, content may also change. After a file is edited, old line numbers may point at new content. File continuations carry a content revision check, and session paging fixes the snapshot it reads, so fragments from different moments are not silently joined. The saved result keeps the content of that particular call for later checking.

Whether the source can be saved is the precondition for omitting content. If saving fails, this layer keeps the incoming result unchanged. Without an available recovery path, shrinking the returned content would lose information permanently, and later calls could not repair it.

Text, images, and data take different paths

A single tool result may contain text, a screenshot, and machine-readable data, each with a different use. Checking whether a button is aligned requires the positional relationship in the screenshot. Judging whether an operation succeeded requires the status the tool returned. The interface and later processing may depend on the full data object. Flattening all of it into short text would discard those separate uses.

So results containing media use the generic text handling. Long text can be saved and shown shortened, while image, audio, and file attachments remain. An image’s content is not reduced to a text note just because the nearby explanation is long.

When sending a request, Wuu puts the text into the tool-result message and gathers the images and files from a consecutive group of tool results into the observation message that follows. The model first receives the textual answer of that group of calls, then receives the screens and attachments they brought back. Audio also travels through file attachments to the adapter layer; whether it can be used depends on the connected model and interface. Content that is only an address and cannot be attached directly is left as a location hint.

Structured data also needs care around duplication. Some tools already provide model-facing content alongside a complete data object. Converting that object to text again may send the same content twice. Wuu keeps the full data in the result and adds a short index to the model input—showing the data’s shape and some keys and values—to reduce repeated carrying.

That index is an overview. It lets the model see the general shape of the result, while the full data remains for the client, extensions, and history replay. Results with only structured data and no other content are first turned into readable text; when they exceed the general limit, they are saved and given a read entry so the tool’s answer can still be read.

Reuse the stable history prefix

These choices finally land in the conversation history. Wuu generates the text projection after the tool finishes, then hands it to the history record. The processed result stays unchanged, and later requests keep using it; content obtained from re-reading is appended through new calls.

The reason for keeping it unchanged is inference caching. Content already in context is reprocessed every turn by the model; if the text differs from one turn to the next, the cache from earlier turns becomes invalid and cannot be reused this turn. So content that has already been sent must not be lightly rewritten. The same old output is not gradually trimmed with each request; what the model first saw stays where it was, and the next read only adds new evidence. The stable history prefix is precisely what lets the cache-hit portion carry over to later requests.

The cost is that some tasks need more reads. Understanding cross-file call relationships, or comparing the full log around an error, may require more material. Judging whether the design works means counting those continuations together: whether each read brings new information, whether the model can complete the next step from it, and how much input the whole task carried.

Adjust the return size by reading behavior

As models change, the amount of information worth returning on first read also changes. A model may make reliable judgments from fewer clues, or become better at reading a large amount at once. We can adjust the budget along the actual reading and continuation behavior, while the saved results keep supplying more information.

Return to that first configuration example: the model reads a value, finds it already explains the problem, and moves on to edit and verify. Or it finds the value depends on a definition elsewhere and reads on. Or it needs to check the content that was just omitted and follows the entry back. The first return gives it a place to start judging; later reads let it gradually gather the content that judgment requires.
