# Memory

The Memory plugin manages three scopes: the **user notebook** keeps long-term
preferences and feedback about you, **workspace memory** keeps facts about a single
workspace that remain valuable across sessions, and **session memory** keeps the
compact state and drafts of the current task. They are all ordinary Markdown files,
not a built-in data model of the core agent loop.

## User notebook

The user notebook keeps personal preferences, feedback, reference information, and
lessons that remain valuable across sessions. It is different from a single
conversation's history, and should not become a copy of project facts or temporary
task logs.

### View memory

After installing and enabling the first-party Memory plugin, open **Settings →
Plugins → Memory**. The settings page, memory prompts, file tools, and management
conversation are all provided by the plugin; the host has no dedicated `/memory`
command or Memory RPC. The panel provides:

- an overview generated from the real notebook;
- refreshing the overview;
- viewing the `MEMORY.md` index and the memory file sources;
- asking in conversation to add, correct, or delete a memory, and viewing the actual
  changed files.

The overview is generated by the plugin through a private Session calling the current
model; use refresh when you need the overview to reflect source changes immediately.
The source view is the direct basis for auditing memory content. Disabling or
uninstalling the Memory plugin removes its page, tools, and prompts together; the
existing Markdown files remain and continue to be used when re-enabled.

### What suits saving

- long-term communication preferences;
- explicit work feedback the user gave;
- reference entry points that still hold across projects;
- lessons that remain useful when you meet a similar problem later.

Do not save keys, raw conversations, short-term task progress, commit SHAs, one-off
logs, or facts you can re-derive directly from the current repository.

### Data and model calls

User memory lives in the memory directory under `~/.wuu` by default; setting
`WUU_HOME` moves all of Wuu's user state together. Generating the overview and
modifying memory through conversation call the current model service; reading the
source files does not need a model.

Memory may be sent to the model as relevant context. Before handling sensitive
content, also check the memory sources, the model service's data policy, and the
[security model](../reference/security-model.md).

## Workspace memory

With the Memory plugin enabled, each workspace has its own `project_memory`: the agent
maintains it during sessions through the plugin-provided `session_memory` tool, and it
keeps stable facts about the workspace that remain valuable across sessions. It lives
in `memory/MEMORY.md` under the workspace state directory, independent of the user
notebook.

Content that suits workspace memory:

- architecture decisions and stable conventions;
- workflow lessons that stay valid long term;
- project background that must carry across sessions.

The same plugin tool also manages session-level files: `summary` (compact resumable
state of the current task), `checkpoint` (legacy compatibility entry), and `notes`
(session drafts). Session-level content belongs to a single active session; do not
rely on it persisting into later sessions. The core only persists ordinary
Session/Turn history and does not recognize or auto-inject these files; the model
reads or updates them when needed according to the Memory plugin's prompt.

## Background memory consolidation (Dream)

The Dream plugin periodically checks finished sessions in the background and
consolidates stable facts worth keeping into workspace memory. It is off by default
and can be enabled in **Settings → Plugins → Dream**, where you can also adjust the
run interval, candidate count, and model alias. Dream writes back through the Memory
plugin's `session_memory` tool, so after disabling Memory it no longer has that
write-back capability. Trigger conditions, configuration, and limitations are in
[background memory consolidation (Dream)](dream.md).

## Difference from project instructions

- Project instructions such as `AGENTS.md` and `CLAUDE.md` continuously affect every
  task in the workspace and suit sharing with the repository;
- the user notebook keeps long-term, cross-project information about the user;
- workspace memory keeps persistent facts about a single workspace.

Project instruction discovery is part of the core's generic prompt input, with the
configuration name `instructions`; the legacy `memory` configuration only migrates at
read time. It is not part of enabling or disabling the Memory plugin, and it does not
read the user or workspace memory files owned by the plugin.

## Memory trust boundary

Memory content enters the agent context and may influence which tools it chooses and
how it handles files. Content written into memory should come from facts you confirmed
yourself, not unverified third-party text; if you find memory has been polluted,
delete the corresponding entries in the memory panel. The ordinary core file tools do
not treat `WUU_HOME` as a general writable directory and cannot bypass the plugin to
read or write user, workspace, or session memory directly; that data is only
accessible through the current generation's Memory plugin capability. The identity
notebooks of collaborative named agents are separate collaboration state, open only
within that agent's explicit file scope, and are not part of the Memory plugin's user
memory interface.
