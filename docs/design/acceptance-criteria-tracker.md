# Local Plugin Customization Acceptance Tracker

This tracker measures working product paths, not type declarations or planned APIs. A capability is complete only when a plugin outside Wuu can use the public contract and an automated test proves activation, use, unload, and failure recovery.

## Current acceptance state

| # | Acceptance criterion | State | Current evidence and remaining work |
|---|---|---|---|
| 1 | Install, approve, enable, disable, and remove from a local directory | Complete | The package lifecycle and CLI cover directory/zip install, exact-fingerprint approval, enable/disable, pending update, and removal. | 2 | Rebuild and reload after a save in development mode | Complete | `wuu plugin dev` runs the package build, validates a candidate, publishes an atomic generation, waits for active generation leases, and preserves the previous generation on build or activation failure. ## Open composition runtime

This matrix records product paths that an independently developed plugin can
use. A bundled implementation is useful evidence only when it goes through the
same public process boundary and SDK; internal Go registries or type declarations
do not count on their own.

| Capability | State | Product evidence and boundary |
|---|---|---|
| Versioned plugin services | Complete | Plugins publish and consume generation-owned services through the public process protocol. Dream reads Memory through that path. Missing providers, incompatible major versions, stopped providers, and failed providers return typed `service_unavailable`; registry inspection exposes only names, versions, providers, methods, and generation identity. Replacement rejects new executions, lets admitted executions finish nested service calls, and cancels the exact execution at the bounded drain deadline. Registry and real cross-process Singlepass tests cover graceful drain and timeout convergence. |
| Exact execution identity, progress, and cancellation | Complete | Tool, capability, kernel-to-plugin service, and nested plugin-to-plugin service dispatches carry one execution ID. Both public runtime SDKs expose that identity, automatically propagate it through nested service calls, and deliver immediate handler cancellation; TypeScript also returns exact Turn/queue cancellation results. Progress is owner-checked, cancellation targets only that live dispatch, and late updates cannot reopen it. Session lineage remains descriptive and does not create a host-owned recursive cancellation tree. |
| Plugin-owned Agent topology | Partial | Public Session services let a plugin create, send to, list, and precisely cancel private Sessions. The bundled Subagent proves the same public path, but an independently maintained plugin has not yet demonstrated a DAG, worker pool, detached worker policy, and custom cancellation propagation. No additional topology API is justified until that consumer exists. |
| Capability staging and command-hook retirement | Partial | Existing capability IDs already represent concrete prompt, pre-step, request-transform, lifecycle, and interruption points. They should be documented against execution stages, but no real consumer requires a generic phase API or shared stage DTO yet. Command hooks remain public and active for Tool mutation and blocking, permissions, files, Sessions, compaction, and Subagent lifecycle, so retirement must proceed event by event only after equivalent consumers migrate. The unused public `actor_path` field is gone; host-owned lineage still evaluates declared root/child `execution_scopes` without exposing an internal path contract. |
| Replaceable loop driver | Partial | The bundled single-pass driver runs in a plugin process, calls model-loop and checkpoint kernel gateways through services, and resumes only from a compatible checkpoint. It still imports private Driver DTOs, selection is process-scoped rather than a durable per-Session fact, and no independently built plugin proves the contract. Current tests resume manually in one process; they do not restart app-server, reload persisted selection and checkpoint state, and prove `resume` rather than `create`. Missing drivers leave stored history readable and reject a new run, but the Thread is not explicitly projected as unavailable/read-only before that attempt. |
| Third-party model provider adapter | Not opened | Provider construction remains hard-coded in `internal/providerfactory`; the existing Kernel Gateway invokes remote Loop Drivers, not plugin Providers. There is no public cross-process provider contract or real external provider consumer. A provider wire contract must not expose internal messages or be added solely to complete this matrix. The first real adapter must drive the provider-neutral request and stream DTOs while Kernel-owned validation preserves Tool call/result ordering, receipts, and legal terminal events. |
| Plugin-owned durable Session events and projections | Partial | Durable Tool history, versioned Presenter snapshots, namespaced state, and renderer fallback exist, but they do not form the required public event → projection → Presenter → generic read-only fallback chain. Plan is the closest concrete migration candidate: its Tool result is already durable, while live `PlanUpdate`, protocol, and Desktop snapshot DTOs remain host-specialized. It does not yet require a plugin-owned cross-restart fact beyond Tool history, so the public event contract must be opened by replacing those seams for a real need, not by relabeling the existing record. Ownership, schema versioning, bounded payloads, Presenter input, missing-plugin fallback, and model-input receipts remain intentionally unimplemented until then. |
| Functional UI and themes compose independently | Partial | Public regions, UI Kit primitives, semantic tokens, Presenter fallback, and generation cleanup are live. The [composition contract test](../../desktop/src/renderer/plugins/ThirdPartyComposition.test.tsx) loads the Deep UI and Manga Studio repository examples together and proves theme cleanup does not remove the functional surface. It does not black-box install and exercise an independently developed functional plugin under the default, dark, and external third-party themes, so §8 acceptance remains open. |
| Headless install, replace, and rollback | Partial | `wuu plugin` covers inspect, install, approve, enable, update, disable, and remove; `wuu plugin dev` preserves the previous package after build or publication failure; `wuu exec` can use installed Tools without Desktop. CLI update approval still promotes a pending package before runtime preflight, unlike the app-server transaction, and there is no deterministic `wuu plugin invoke` entry backed by `plugin/client/request`. A persistent app-server black-box flow must still prove install v1 → invoke → replace with v2 → reject broken v3 activation → invoke v2. |
| Observer, Presenter, and background failure isolation | Partial | Turn observers run outside terminal publication with bounded delivery, renderer failures preserve host fallback, and Automation/Dream background failures do not enter Turn finalization. Focused tests prove those mechanisms separately, but no independently installed plugin has combined an observer failure, Presenter failure, and plugin-owned background/process failure while a public app-server Session durably commits its terminal Turn and remains usable. No generic background-task API is justified by this gap. |
| First-party/public-entry parity | Complete | Distributed first-party feature code uses the public SDK, process protocol, host services, UI regions, and Presenter APIs. Production lifecycle tests prove generation replacement and full removal without private React state or product-specific host actions. Bundled manifests use host-owned official helper resolution and bypass user approval as distribution/trust machinery; those entries do not grant a product capability unavailable to an ordinary plugin executable using the public runtime command. |

## Completion rules

- A public interface, registry, manifest field, or protocol struct alone counts as **Partial**, never **Complete**.
- Every executable contribution must be owned by one plugin generation and disappear after disable, uninstall, upgrade, failed activation, or development reload.
- Every renderer must have a host fallback that preserves Settings, plugin disable, and default UI recovery.
- Development authorization is directory-specific and must never transfer to a normal downloaded package.
- The acceptance plugin must build and test outside the Wuu source tree using only the public SDK and documented commands.
- Marketplace, hosted publishing, remote automatic update, ranking, and remote dependency resolution are not acceptance requirements.

## Implementation lanes

1. Preserve the public SDK artifact from the first SDK-bearing release, then add it as the previous-minor input to the next release's host compatibility matrix.
2. Keep the standalone acceptance plugin in release checks for runtime and renderer contracts.
3. Run a real Desktop install, restart, upgrade, failed activation, failed render, disable, and removal smoke test before each release.
